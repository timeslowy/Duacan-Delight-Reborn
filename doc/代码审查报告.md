## 二、致命问题 (Fatal)

### F1. VillageCropModifier 使用反射修改不可变字段

**文件**: `src/main/java/by/timeslowly/duacan_delight/common/world/VillageCropModifier.java:47-58`

**问题描述**:
通过反射直接修改 `StructureProcessorList` 的私有 `list` 字段。该字段在 Minecraft 1.21.1 中被声明为 `final`，底层实现为 `List.copyOf()` 返回的不可变列表。在 Java 21 的模块系统限制下，此反射操作可能：

1. 直接抛出 `InaccessibleObjectException`（Java 模块系统拦截）
2. 修改不可变列表导致 `UnsupportedOperationException`
3. 每次单机世界重启时，由于注册表是全局持久的，会重复追加处理器规则，造成数据累积

**修复方案**:
移除反射方式，改用 NeoForge 提供的 `RegisterStructureProcessorsEvent` 事件或数据包方式添加处理器。

```java
// 方案一：使用 NeoForge 事件（需要在 modEventBus 上注册）
@EventBusSubscriber(modid = Duacan_delight.MOD_ID, bus = EventBusSubscriber.Bus.MOD)
public class VillageCropModifier {
    @SubscribeEvent
    public static void registerProcessors(RegisterStructureProcessorsEvent event) {
        // 在这里注册自定义的 StructureProcessor
    }
}

// 方案二（推荐）：使用数据包 datapack 方式，通过 JSON 定义 biome_modifier
// 或 structure_modifier 来完成，无需任何 Java 代码
// 参考: data/duacan_delight/neoforge/biome_modifier/ 下的现有 JSON 配置
```

**影响**: 服务器启动时可能直接崩溃；模块化环境下必现。

**修复状态**: ✅ **已修复** — 移除 `VillageCropModifier.java`，改用数据包 JSON 覆写方式。在 `src/main/resources/data/minecraft/worldgen/processor_list/` 下创建了 5 个 JSON 文件，完整覆写原版农田处理器列表并追加盖菜作物规则。删除了 `Duacan_delight.java` 中的事件监听器注册。

### F2. TremellaSporeItem 物品使用存在物品复制漏洞

**文件**: `src/main/java/by/timeslowly/duacan_delight/common/item/TremellaSporeItem.java:50-55`

**问题描述**:
在 `useOn` 方法中，先调用 `level.setBlock(...)` 放置方块，然后使用 `clearOrCountMatchingItems` 消费物品，且参数使用了 `inventoryMenu.getCraftSlots()` 而非玩家背包。此写法存在以下问题：

1. 如果 `setBlock` 成功但后续物品消费失败（或中途取消），方块已经放置但物品未消耗
2. `getCraftSlots()` 返回的是合成容器的槽位引用，在非合成场景下可能为空容器，导致物品根本不会被消费
3. 使用 `clearOrCountMatchingItems` 遍历背包的做法效率低且易出错

**修复方案**:
使用标准的 `ItemStack#shrink(1)` 或在放置方块前先检查条件完备性，确保"先验证后操作"的模式：

```java
@Override
public @NotNull InteractionResult useOn(@NotNull UseOnContext context) {
    Level level = context.getLevel();
    BlockPos pos = context.getClickedPos();
    BlockPos above = pos.above();

    if (!level.getBlockState(pos).is(BlockTags.LOGS)) {
        if (context.getPlayer() != null && !level.isClientSide())
            context.getPlayer().displayClientMessage(Component.translatable("message.duacan_delight.invalid_plant_block"), true);
        return InteractionResult.FAIL;
    }

    if (level.getBrightness(LightLayer.BLOCK, above) > 8 || level.getBrightness(LightLayer.SKY, above) >= 8) {
        if (context.getPlayer() != null && !level.isClientSide())
            context.getPlayer().displayClientMessage(Component.translatable("message.duacan_delight.light_too_strong"), true);
        return InteractionResult.FAIL;
    }

    if (!level.getBlockState(above).is(Blocks.AIR)) {
        return InteractionResult.FAIL;
    }

    if (!level.isClientSide()) {
        level.setBlock(above, DDBlocks.TREMELLA_CROP.get().defaultBlockState(), 3);
        context.getItemInHand().shrink(1);  // ← 标准做法
    }
    return InteractionResult.SUCCESS;
}
```

**影响**: 可能导致玩家在特定条件下无限刷取物品（物品复制漏洞）。

**修复状态**: ✅ **已修复** — 将 `clearOrCountMatchingItems` 替换为标准的 `context.getItemInHand().shrink(1)`。增加了 `level.setBlock()` 返回值检查（放置失败不消耗物品）和创造模式检查（`instabuild` 玩家不消耗）。

## 三、错误 (Error)

### E1. DDFluids 使用了已弃用的 ItemBlockRenderTypes API

**文件**: `src/main/java/by/timeslowly/duacan_delight/registry/DDFluids.java:25-33`

**问题描述**:
`ItemBlockRenderTypes.setRenderLayer()` 在 NeoForge 1.21.1 中已被标记为 `@Deprecated`。新的推荐做法是通过 `RegisterClientExtensionsEvent` 注册 `IClientFluidTypeExtensions`（流体类已在 `SoybeanMilkFluidFluidType` 和 `TeaoilFluidFluidType` 中正确实现），或通过方块的 JSON 模型数据来指定渲染层。

流体渲染层的设置应放在 `FluidType` 的客户端扩展注册中（已在两个 `FluidType` 子类中通过 `RegisterClientExtensionsEvent` 正确处理），**无需**再单独调用 `ItemBlockRenderTypes.setRenderLayer()`。

**修复方案**:
删除 `FluidsClientSideHandler` 内部类，因为 `SoybeanMilkFluidFluidType` 和 `TeaoilFluidFluidType` 已经通过 `RegisterClientExtensionsEvent` 正确注册了纹理和渲染属性。

**影响**: 使用弃用 API，未来版本可能移除；虽当前仍可运行，但不合规范。

**修复状态**: ✅ **已修复** — 删除了 `DDFluids.java` 中整个 `FluidsClientSideHandler` 内部类及其 8 个弃用的 import。流体渲染层已通过 `SoybeanMilkFluidFluidType` 和 `TeaoilFluidFluidType` 中的 `RegisterClientExtensionsEvent` + `IClientFluidTypeExtensions` 正确处理。

### E2. DDItems 中 BucketItem 引用 DeferredHolder.get() 存在静态初始化顺序风险（误报）

**文件**: `src/main/java/by/timeslowly/duacan_delight/registry/DDItems.java:126-127`

**问题描述**:
```java
public static final DeferredItem<Item> SOYBEAN_MILK_FLUID_BUCKET = REGISTRY.register("soybean_milk_fluid_bucket",
    () -> new BucketItem(DDFluids.SOYBEAN_MILK_FLUID.get(), ...));
```

`BucketItem` 构造函数接收 `Fluid` 对象，代码中在 lambda 外调用了 `.get()`。虽然 `DeferredRegister` 机制在注册阶段会推迟执行，但此处 `.get()` 在注册条目创建时即被求值（作为 lambda 捕获的变量），而非在 lambda 执行时。应使用 `Supplier<Fluid>` 或在 lambda 内部调用 `.get()`。

**修复方案**:
```java
// 修改为在 lambda 内部调用 .get()
public static final DeferredItem<Item> SOYBEAN_MILK_FLUID_BUCKET = REGISTRY.register("soybean_milk_fluid_bucket",
    () -> new BucketItem(DDFluids.SOYBEAN_MILK_FLUID.get(), new Item.Properties().craftRemainder(Items.BUCKET).stacksTo(1).rarity(Rarity.COMMON)));
```

实际上 `DeferredRegister` 延迟注册机制确保此时 `SOYBEAN_MILK_FLUID` 已注册，但使用 lambda 内部求值是更安全的模式。

**影响**: 在特定类加载顺序下可能 NPE，目前因 NeoForge 的类加载保证而未暴露。

## 五、建议 (Suggestion)

### S1. 大量 Item 子类仅用于添加单行描述文本

**涉及文件**: ~30 个 `common/item/` 下的类（如 `OysterItem.java`, `OysterShellItem.java`, `GodongguiItem.java`, `GuojiaoItem.java` 等）

**问题描述**:
许多物品类仅重写 `appendHoverText` 方法添加一行翻译文本，没有额外的独特逻辑。这导致 47 个物品类中约 30 个是冗余的。

**优化建议**:
创建一个通用的 `TooltipItem` 类，在注册时传入翻译键后缀：

```java
public class TooltipItem extends Item {
    private final String descriptionKey;
    
    public TooltipItem(Properties properties, String descriptionKey) {
        super(properties);
        this.descriptionKey = descriptionKey;
    }
    
    @Override
    public void appendHoverText(ItemStack stack, TooltipContext context, List<Component> list, TooltipFlag flag) {
        super.appendHoverText(stack, context, list, flag);
        list.add(Component.translatable(descriptionKey));
    }
}
```

这样可以删除约 30 个冗余类文件。

**修复状态**: ✅ **已修复** — 创建了支持可变数量描述键的 `TooltipItem` 类。47 个仅含工具提示的物品类全部替换为 `DDItems.java` 中的 lambda 注册。`common/item/` 目录从 60 个类减少到 14 个。

## 六、亮点总结

1. **注册系统规范**: 全部使用 `DeferredRegister`，清晰分离到 7 个注册类，符合 NeoForge 最佳实践。

2. **食物效果提示工具**: `FoodEffectTooltipHandler` 自动从 `FoodProperties` 提取药水效果并插入物品提示，避免手动编写效果文本，这是一个精巧的设计。

3. **菜系标签系统**: `CuisineTooltipHandler` 使用自定义标签自动为物品附加菜系信息，比硬编码灵活且易于扩展。

4. **LootModifier 实现规范**: `TremellaSporeModifier` 的 CODEC 使用 `RecordCodecBuilder`，正确实现了 JSON 序列化/反序列化。

5. **流畅的流体系统**: 两个流体（豆浆和茶油）的 Fluid/FluidType 架构完整，`IClientFluidTypeExtensions` 客户端扩展注册正确。

6. **跨模组兼容性**: 提供了多个可选模组的配方集成（Create、Butchercraft、Cuisine Delight 等），数据包结构清晰。

7. **从 MCreator 到 IDE 的完整重写**: 项目已成功脱离 MCreator 框架，采用标准 NeoForge 架构，代码质量和可维护性有根本性提升。
